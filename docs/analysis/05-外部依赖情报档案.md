## 2. Thinking Mode 接入规格（可直接编码）

### 2.1 三种 API 格式的确切参数（官方原文）

| | OpenAI Chat Completions | Anthropic Messages | Responses API |
|---|---|---|---|
| **思考开关** | 顶层 `{"thinking": {"type": "enabled"}}` / `"disabled"` | `{"reasoning": {"effort": "none/low/high/max"}}`（`none` 禁用思考）；或 `thinking.type` | `{"reasoning": {"effort": "low/high/max"}}` |
| **思考强度** | 顶层 `"reasoning_effort": "low" / "high" / "max"` | `{"output_config": {"effort": "low/high/max"}}` | 同 `reasoning.effort` |
| **默认值** | **thinking 默认 enabled，effort 默认 high** | 同 | 同 |

- Flash 与 Pro 的 effort 映射表完全一致：`low→low`、`medium→high`、`high→high`、`xhigh→high`、`max→max`。即 **medium/xhigh 是兼容输入，实际只有 low/high/max 三档**。
- 用 OpenAI Python SDK 时 `thinking` 需放 `extra_body`（SDK 会在发请求前合并到顶层）；**在 wire 层面 `thinking` 就是一个普通顶层 JSON 字段**——青山用 URLSession 手写请求时直接放顶层即可。

### 2.2 思考模式下的输入限制

- `temperature` / `top_p` / `presence_penalty` / `frequency_penalty` **无效**（不报错、不生效）——传了也白传，且无错误信号。
- 非思考模式这些参数正常生效。→ 青山若要在两种模式间切换，采样参数应随模式一起条件化。

### 2.3 输出与流式行为

- 非流式：`choices[0].message.reasoning_content` 与 `content` 同级。
- 流式（SSE）：CoT 在 **`choices[0].delta.reasoning_content`**，正文在 `delta.content`。`reasoning_content` 先流完，再流 `content`。
- **Chat Completions 流以 `data: [DONE]` 结束；但 DeepSeek 可能插入 `:` 开头的 keep-alive 注释行**——自研 SSE 解析器必须跳过注释行（ Responses API 无 [DONE]）。

### 2.4 ⚠️ 多轮 + tools 的 reasoning_content 回传规则（最大坑）

- 请求**不带 tools**：历史轮次的 `reasoning_content` 不需要回传；传了也会被忽略、不进上下文。
- 请求**带 tools**：**所有历史 assistant 消息（包括没有产生 tool call 的轮次）的 `reasoning_content` 必须原样完整回传**，否则 API 返回 **400**：`The "reasoning_content" in the thinking mode must be passed back to the API`。
- 官方推荐：直接把 `response.choices[0].message`（含 content / reasoning_content / tool_calls 三字段）整体 append 回 messages。
- 截断或摘要 reasoning_content 也可能在部分版本上被拒。

**青山编码要求**：消息存储层必须持久化 `reasoning_content` 字段；带 tools 的 agent 循环回放历史时不得剥离该字段。

来源（2026-09-05 查证）：https://api-docs.deepseek.com/guides/thinking_mode 、https://api-docs.deepseek.com/guides/tool_calls

## 3. Responses API 与 Codex 适配调研

### 3.1 端点与基本形态

- 端点：`POST https://api.deepseek.com/responses`（base_url 与 Chat Completions 相同）。
- 请求核心字段：`model`、`input`（字符串或 input item 数组）与/或 `instructions`（插入为第一条 system）、`stream`、`temperature`（思考模式无效）、`max_output_tokens`、`tools`、`tool_choice`、`reasoning.effort`。
- **无状态**：`previous_response_id` / `conversation` / `store` / `background` / `metadata` 均不支持；`store` 恒为 false。**不支持的参数一律静默忽略、不报错**。
- 超出上下文窗口返回 400（无服务端 truncation）。

### 3.2 流式事件（与 Chat Completions 完全不同的契约）

- SSE 语义事件，带 `event` 字段与单调递增 `sequence_number`；**没有 `data: [DONE]`**，以 `response.completed` / `response.incomplete` / `response.failed` 收尾。
- 关键事件：`response.created` → `response.output_item.added/done`（item 类型：reasoning / message / function_call / custom_tool_call / web_search_call）→ `response.reasoning_text.delta/done`（CoT 增量）→ `response.output_text.delta/done`（正文增量）→ `response.function_call_arguments.delta/done` → `response.completed`（含完整 usage）。
- JSON 输出用 `text.format`（`json_object` 或 `json_schema`），非 `response_format`。

### 3.3 工具差异

- 支持 `function`、`web_search`（服务器端执行，自动续跑上限 10 轮）、`custom: {"name": "apply_patch"}`（Codex 兼容）；`file_search`/`code_interpreter`/`mcp` 等**被忽略**。
- `parallel_tool_calls` 参数被忽略——**并行工具调用始终开启**。
- `reasoning.summary` 接受但不产出摘要。

### 3.4 Codex 适配结论

- DeepSeek 官方专门为 Codex 适配了 V4-Flash（Terminal-Bench 2.1 = 82.7 等 agent 基准即以 Harness minimal mode + max effort 跑出），官方文档提供一键配置脚本：`~/.codex/config.toml` 中 `wire_api = "responses"`、`base_url = "https://api.deepseek.com/"`。
- **对青山的可借鉴点**：Responses API 的事件流模型（output_item 抽象 + reasoning 独立事件）比 Chat Completions 的 delta 更适合 agent 循环；但青山当前走 OpenAI 兼容中转站，**中转站普遍不转发 `/responses` 端点**，接入前必须实测。稳妥路径仍是 Chat Completions。

来源（2026-09-05 查证）：https://api-docs.deepseek.com/guides/responses_api

## 4. 官方 Harness（dsh）与 function calling 稳定性

### 4.1 DeepSeek Harness

- 定位：DeepSeek 官方开源 Agent 运行时框架，开发者预览 v0.1 于 2026-08-13 公开。仓库 `github.com/deepseek-ai/deepseek-harness`，npm 包 `@deepseek-ai/dsh`（CLI 命令即 `dsh`），Node.js 22.19+，Web UI 默认 127.0.0.1:3080。
- **四种模式**：Standard（全功能编码 Agent）、Code/PTC（模型写 TypeScript 组合多步工具）、**Minimal（仅 bash + str_replace_editor 两个工具——官方 V4 Agent 基准即在此模式跑出，用于纯模型基线评测）**、Creator（插件实验/自定义 preset）。
- 全轨迹 append-only 日志：可 resume/fork/replay 会话。
- ⚠️ 预览版，API 与插件接口有 breaking change 风险（npm 版本 0.1.0-rc.6，无正式 release tag）。
- 与青山关系：dsh 是参考实现而非依赖——重点参考其 minimal-mode 工具面（bash+编辑器）与轨迹日志设计。

来源（2026-09-05 查证）：https://github.com/deepseek-ai/deepseek-harness 、https://deepseek.com/ 、CSDN/dev.to 评测文（二手，已与官方仓库交叉印证）

### 4.2 function calling 在 V4 上的稳定性

- 官方能力矩阵 Tool Calls = ✓（三模型全支持），思考/非思考模式均可用（自 V3.2 起思考模式支持工具调用）。
- **strict mode（Beta）**：需 ① `base_url = "https://api.deepseek.com/beta"`；② 每个 function 设 `"strict": true`；③ 服务端校验 JSON Schema。支持子集：object / string / number / integer / boolean / array / enum / anyOf / `$ref` / `$def`。硬性要求：**所有 object 的属性必须全部 required 且 `additionalProperties: false`**；string 不支持 minLength/maxLength（支持 pattern、format: email/hostname/ipv4/ipv6/uuid）；array 不支持 minItems/maxItems。
- 并行工具调用：Responses API 恒开；Chat Completions 上官方未暴露 `parallel_tool_calls` 开关，但模型单轮可返回多个 `tool_calls`（官方示例即多工具链式调用）。
- **稳定性综合判断**：单轮 tool_calls 可用；strict mode 生产可用性一般（beta + schema 子集严格）；最大风险不是"不调用"而是第 2.4 节的 reasoning_content 回传 400——这是社区报告最多的故障（opencode、claude-code-router、n8n、openclaw 均有 issue）。

来源（2026-09-05 查证）：https://api-docs.deepseek.com/guides/tool_calls

## 5. 中转站（OpenAI 兼容网关）兼容性风险清单

按风险等级排序，均已找到社区实例或机制性依据：

| # | 风险 | 机制 | 后果 | 检测方法 |
|---|---|---|---|---|
| 1 | **thinking 开关被剥离** | `thinking` 是非标顶层字段（OpenAI SDK 经 extra_body 合并）。中转站若"重建/归一化"请求体而非逐字转发，会丢弃该字段 | **静默降级**：思考被关或落到服务端默认，无任何报错，计费照常 | 检查响应是否有 `reasoning_content` |
| 2 | **reasoning_content 回传被剥离 → 400** | 中转站/客户端框架重建 history 时只保留 role/content/tool_calls，丢掉 reasoning_content | 带 tools + 思考模式的多轮请求第二轮起 400（opencode/claude-code-router/n8n/openclaw 实例） | 2 轮工具链路冒烟测试 |
| 3 | **流式 delta.reasoning_content 被丢** | 部分中转站的 SSE 转换器只认识 delta.content | CoT 丢失（正文正常），agent 无法回传 CoT | 流式冒烟测试 |
| 4 | **keep-alive 注释行** | DeepSeek 官方流会插入 `:` 开头注释；部分中转站转发后青山解析器若未跳过注释会崩溃 | 解析异常 | 长等待请求观察 |
| 5 | **/beta 与 /responses 端点不转发** | strict mode、FIM、Chat Prefix Completion 走 /beta；Codex 走 /responses | 404 或兼容层伪装失败 | 端点探测 |
| 6 | **reasoning_effort 被白名单过滤** | 非标枚举参数 | effort 静默变默认 high | 对比 max 与 low 的首 token 延迟 |
| 7 | **静默忽略文化的掩盖效应** | DeepSeek/中转站对不支持的参数一律不报错 | 错误配置长期不可见 | 建立参数回显/usage 断言 |
| 8 | **模型名映射** | 部分中转站把未知模型名自动映射到默认模型（Anthropic 格式下 DeepSeek 官方也会把未知名映射到 v4-flash） | 以为在用 Pro 实际在用 Flash | usage/响应头核对 |

**青山对策建议**：
1. 请求构建层（青云 LLMService）逐字拼接 JSON body，不做"字段白名单归一化"；
2. 消息存储层持久化 `reasoning_content` 并在带 tools 请求中原样回放；
3. SSE 解析器跳过 `:` 注释行、兼容 `delta.reasoning_content` 缺失；
4. 首次接入任一中转站跑"四件套冒烟"：非思考单轮 → 思考单轮 → 思考+工具两轮 → 思考流式，全部通过才入库。

来源（2026-09-05 查证）：https://therouter.ai/news/deepseek-v4-reasoning-effort-proxy-routing 、https://www.coderouter.io/blog/deepseek-reasoning-content-400-error-fix 、https://github.com/openclaw/openclaw/issues/79608

## 6. iOS 平台情报

### 6.1 后台执行（对 Agent 类 App 的直接约束）

- **iOS/iPadOS 26 新增 `BGContinuedProcessingTask`**：仅限"用户在前台明确启动的任务"延续到后台（如导出、发布），系统以 Live Activity 展示进度、用户可取消；**系统会因进度停滞而终止任务**；支持后台 GPU 访问。它**不能**用来做"定时自动执行"——任务必须从前台开始。
- `BGAppRefreshTask` 是**启发式调度，不保证固定间隔**（Quinn "The Eskimo"：期望每 15 分钟一次必失望，甚至可能完全不给时间）；实测：用户 1–2 周不打开 App，系统会逐步减少直至停止后台任务；用户 force quit 后系统禁止后台拉起（无文档化豁免）。
- 静默推送（background notification）由系统酌情执行、低优先级，不可依赖。
- 后台 API 用途受 App Review 条款 2.5.4 约束。
- **青山结论**：长时 Agent 任务（用户点"开始"后的多步工具链）→ 用 `BGContinuedProcessingTask` + 进度上报 + 到期 handler + 幂等断点续跑；任何"定时巡检"类需求在 iOS 上天然不可靠，应设计为"打开 App 时补偿执行"。

来源（2026-09-05 查证）：https://developer.apple.com/videos/play/wwdc2025/227/ 、Apple Developer Forums (Core OS / Quinn) 、https://calcopilot.app/blog/posts/running-ios-background-tasks-reliably-part1

### 6.2 TrollStore

- **TrollStore 不支持 iOS 26**（也不支持 iOS 18/17.0.1+）。依赖 CoreTrust 漏洞 CVE-2023-41991，Apple 已于 iOS 17.0.1 修补，无新公开利用。支持范围：iOS 14–16.6.1（TrollInstallerX）与 iOS 17.0（TrollRestore）。
- 网上所有"TrollStore for iOS 26"均为钓鱼/点击诱饵。
- iOS 26 上的实际替代：LiveContainer（无需越狱绕 3-app 限制）、SideStore、Feather、AltStore/PAL、Gbox（支持 iOS 26–26.4）——均为常规签名/容器方案，**没有免签永装**。

来源（2026-09-05 查证）：https://trollstore.app/ 、https://ios18apps.com/trollstore-ios-26 、http://onejailbreak.com/blog/trollstore-ios-26/
